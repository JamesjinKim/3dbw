# IIS3DWB 보드 검사 (boardcheck)

센서 보드를 USB 로 꽂고 명령 하나를 실행하면, **20초 안에 6개 항목을 검사하고
PASS / FAIL 을 판정**합니다. 하드웨어를 변경했을 때, 그리고 새 보드를 받았을 때
소프트웨어 작업에 들어가기 전에 먼저 돌리는 관문입니다.

WiFi 설정도 NVS 주입도 필요 없습니다. 꽂고 실행하면 끝입니다.

---

## 빠른 사용법

```bash
cd boardcheck
./run.sh              # 보드 한 개 검사
./run.sh --loop       # 보드를 갈아 끼우며 연속 검사 (Ctrl+C 로 종료)
```

출력 예 (정상 보드):

```
[1/6] MCU               PASS  ESP32-S3 rev0.2, 2코어, flash 2048KB, MAC 30:ED:A0:1A:8A:44
[2/6] SPI / WHO_AM_I    PASS  WHO_AM_I=0x7B (기대 0x7B)
[3/6] 가속도 출력       PASS  X=11 Y=-60 Z=973 mg, |a|=975 mg, p2p=1081 LSB
[4/6] FIFO / ODR        PASS  212워드 / 8.0ms → 26583 Hz (사양 26667 Hz)
[5/6] INT1 전기상태     PASS  IO4 풀업=1 풀다운=1 플로팅=1 (FIFO=345 WTM=1, INT1_CTRL=0x08)
[6/6] INT 발생률        PASS  4112회/10.0초 = 411/s (기대 416/s), 샘플 26768 Hz, 오버런 1
────────────────────────────────────────────────────────────────
 참고  INT2(IO5) 풀업=0 풀다운=0 → LOW 구동
════════════════════════════════════════════════════════════════
  판정: PASS   (실패 0 · 주의 0 · 전체 6)
```

로그는 `results/` 에 `날짜_MAC_판정.log` 로 자동 보관됩니다.

**종료 코드** — CI 나 스크립트에서 쓸 때:

| 코드 | 뜻 |
|---|---|
| 0 | PASS |
| 1 | WARN (동작은 하지만 확인 필요) |
| 2 | FAIL (불량) |
| 3 | 실행 오류 (보드 미연결, 플래시 실패 등) |

## 필요한 것

담당자 쪽 PC(라즈베리파이 또는 리눅스)에 아래만 있으면 됩니다. **ESP-IDF 는
필요 없습니다** — 구워질 펌웨어가 `dist/` 에 이미 들어 있습니다.

```bash
sudo apt install python3 python3-serial esptool
sudo usermod -aG dialout $USER     # 실행 후 로그아웃·재로그인
```

## 검사 항목

| # | 항목 | 무엇을 보는가 | FAIL 이면 |
|---|---|---|---|
| 1 | MCU | ESP32-S3 인지, MAC·플래시 크기 | 보드 MCU 가 다름 |
| 2 | SPI / WHO_AM_I | SPI 로 센서와 대화되는지 (0x7B) | MISO 단선 / CS 미동작 / 센서 전원 |
| 3 | 가속도 출력 | 정지 시 중력 1g 가 보이는지, 값이 고정돼 있지 않은지 | 센서가 변환을 하지 않음 |
| 4 | FIFO / ODR | FIFO 축적 속도로 ODR(26,667 Hz) 역산 | 센서 클럭 이상 / 레지스터 미적용 |
| 5 | **INT1 전기상태** | watermark 도달 시점에 INT1 핀이 실제로 구동되는지 | **단선 / 극성 반전** |
| 6 | INT 발생률 | 인터럽트가 초당 몇 번 오는지 (기대 ≒417) | 간헐 접촉 불량 / 노이즈 |

### 5번이 이 툴을 만든 이유

보드 한 개에서 **INT1 이 플로팅(단선)** 이라 인터럽트 모드가 동작하지
않았습니다. 그런데 펌웨어는 조용히 폴링으로 흘러가 "왜 느리지?" 라는 증상만
남겼고, 원인을 찾는 데 오래 걸렸습니다.

핀에 내부 풀업·풀다운을 번갈아 걸어 보면 원인이 한 번에 갈립니다:

| 풀업 | 풀다운 | 판정 |
|---|---|---|
| 1 | 1 | **HIGH 로 능동 구동 = 정상** (센서가 신호를 보내고 있음) |
| 1 | 0 | 아무도 구동 안 함 = **단선** |
| 0 | 0 | LOW 로 능동 구동 = **극성 반전** |

INT2(IO5)를 대조군으로 함께 읽으므로, INT1 만 끊긴 것인지 커넥터 전체가
문제인지도 바로 구분됩니다.

## 핀맵을 바꿨다면

핀 정의는 **`../components/iis3dwb/Kconfig` 한 곳**에만 있습니다.
운영 펌웨어와 검사 펌웨어가 같은 파일을 읽으므로, 한쪽만 고쳐져 어긋날 일이
없습니다.

```bash
cd boardcheck
idf.py menuconfig      # Component config → IIS3DWB Vibration Sensor Configuration
./build.sh             # 다시 빌드 → dist/ 갱신
```

빌드 로그와 `dist/manifest.json` 에 검사에 쓰인 핀맵이 기록되고,
`./run.sh` 실행 시에도 화면에 표시됩니다. **검사 결과를 받을 때는 핀맵이
같이 찍혔는지 확인하세요** — 다른 핀맵으로 돈 PASS 는 의미가 없습니다.

판정 기준(INT 발생률 상·하한, ODR 하한, 측정 시간)도 menuconfig 의
`Board Check` 메뉴에서 조정할 수 있습니다.

## 담당자에게 전달하는 방법

`boardcheck/` 폴더를 통째로 복사해 주면 됩니다. 단, 호스트 스크립트가
`../sensor-setup-py/` 의 esptool 래퍼를 쓰므로, 저장소 밖으로 뺄 때는
그 두 모듈을 `boardcheck/lib/` 에 함께 넣어 주세요.

```bash
mkdir -p boardcheck/lib
cp sensor-setup-py/esp_flash.py sensor-setup-py/usb_reset.py boardcheck/lib/
tar czf boardcheck.tar.gz boardcheck/
```

`build/` 는 빼도 됩니다 (`dist/` 만 있으면 검사가 돕니다).

## 자주 겪는 문제

**포트를 못 찾습니다**
충전 전용 USB 케이블인 경우가 대부분입니다. `dmesg | tail` 로 장치가 잡히는지
확인하세요. 포트가 여러 개면 `./run.sh --port /dev/ttyACM0` 로 지정합니다.

**굽는 중 멈춥니다 (USB 스톨)**
라즈베리파이에서 흔합니다. 스크립트가 자동으로 USB 장치를 리셋하고 한 번 더
시도합니다. 그래도 안 되면 케이블을 뽑았다 꽂으세요.

**"검사가 끝나지 않았습니다"**
보드가 부팅 중 리셋을 반복하고 있을 수 있습니다. 위에 찍힌 보드 로그를
그대로 보내 주세요.

## 검사 후 보드 상태

검사 펌웨어는 **NVS(0x9000)를 건드리지 않습니다.** 파티션 표도 운영 펌웨어와
같으므로, 검사가 끝난 보드에 운영 펌웨어를 다시 구우면 기존 설정(WiFi·서버
IP 등)이 그대로 살아 있습니다.

검사 펌웨어는 판정을 출력한 뒤 멈춰 있습니다. 다시 검사하려면 USB 를 뽑았다
꽂거나 `./run.sh --no-flash` 를 실행하세요 (굽지 않고 재부팅해 재검사).
