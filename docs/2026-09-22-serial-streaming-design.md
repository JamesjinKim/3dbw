# Design: USB 시리얼 직결 전송 + 공장 초기화

- **Feature**: serial-streaming
- **작성일**: 2026-09-22
- **관련 설계**: [[wifi-sensor-streaming.design]], [[gui-server-config.design]]

## 1. 배경과 목표

현재 IIS3DWB 디바이스는 WiFi에 접속해 UDP로 진동 데이터를 서버에 전송한다.
여기에 **USB 케이블로 PC에 직접 전송하는 경로**를 선택적으로 추가한다.
WiFi가 없거나 불안정한 현장, 또는 PC에 직결해 바로 데이터를 받고 싶은 경우를 위한 것이다.

추가로 **공장 초기화 기능**을 GUI에 넣어, 저장된 설정을 지우고 재설정할 수 있게 한다.

### 확정된 결정사항

| 항목 | 결정 |
|------|------|
| 전송 속도 | WiFi와 동일 — 최대 26.6 kHz까지 지원 |
| WiFi와의 관계 | **배타 선택** — 시리얼 선택 시 WiFi 연결 안 함 |
| 로그 충돌 해결 | **스트리밍 중 로그 자동 차단** (데이터 전용 모드) |
| 설정 방법 | 기존 방식 유지 — GUI에서 설정 → NVS 주입 |
| 보드레이트 | GUI에 노출하지 않음 (수신 툴 내부에만) |
| 기본 속도 | 3.3 kHz (WiFi와 동일) |
| 복구 경로 | 부팅 후 3초 명령 대기 창 |
| 공장 초기화 범위 | 설정(NVS)만 삭제, 펌웨어 유지 |

### 범위 밖 (별도 진행)

**수신 프로그램은 이 작업에 포함하지 않는다.**
라즈베리파이(EDU Kit WDAQ)에서 별도로 개발하며, GPIO 포토센서 값에 따라
수신을 시작(True)/중단(False)하는 게이팅 로직을 포함한다.
이 문서의 [7장 패킷 계약](#7-wdaq-수신-측-계약-송신-사양)이 그 작업의 입력 사양이다.

## 2. 왜 115200에서 26.6 kHz가 가능한가

사용자 질문에서 나온 핵심 쟁점이므로 근거를 남긴다.

**115200 bps가 진짜 UART 제약이라면:**

```
115200 bps ÷ 10 비트/바이트(8N1) = 11,520 B/s
샘플 1개 = 6바이트, 패킷 오버헤드 = 16B/200샘플 = 0.08B
→ 11,520 ÷ 6.08 ≈ 1,894 Hz (이론 최대)
→ 실용 상한 약 1,500 Hz
```

이 경우 1 kHz 옵션 하나만 쓸 수 있다.

**그러나 ESP32-S3의 USB 포트는 USB Serial/JTAG (USB CDC-ACM)이다.**
진짜 UART가 아니라 USB Full-Speed(12 Mbps) 위에서 동작한다.
CDC에서 보드레이트는 호스트 드라이버에 전달되는 형식적 값일 뿐이고,
펌웨어는 그 값을 참조하지 않으며 실제 전송률을 제한하지 않는다.

**USB CDC 실측 스루풋 기준 (보수적으로 500 KB/s):**

| rate_step | 속도 | 필요 대역폭 | 115200 UART | USB CDC |
|-----------|------|------------|-------------|---------|
| 0 | 1 kHz | 6.1 KB/s | ✅ 여유 47% | ✅ 여유 99% |
| 1 | 3.3 kHz | 20.1 KB/s | ❌ 1.7배 초과 | ✅ 여유 96% |
| 2 | 6.6 kHz | 40.1 KB/s | ❌ 3.5배 초과 | ✅ 여유 92% |
| 3 | 13.3 kHz | 80.9 KB/s | ❌ 7배 초과 | ✅ 여유 84% |
| 4 | 26.6 kHz | 161.7 KB/s | ❌ 14배 초과 | ✅ 여유 68% |

**결론: 대역폭은 병목이 아니다. 실제 위험은 채널 공유(로그 충돌)다.**

### 검증이 필요한 가정

위 500 KB/s는 일반적인 USB CDC 실측치이며, **이 펌웨어·이 보드에서
26.6 kHz가 유실 없이 나오는지는 실기기 측정으로 확인해야 한다.**

ESP32-S3의 USB Serial/JTAG는 내부 FIFO가 64바이트 단위로 작아,
고속에서 쓰기 블로킹이 발생하면 tx_task가 밀리고 → 링버퍼 오버런 →
센서 샘플 유실로 이어질 수 있다.

**측정 기준**: `sensor_streamer_stats_t.dropped` 가 0에 가까운지.
이 측정으로 실제 상한을 확정한다.

## 3. 전송 계층 추상화 (sensor_streamer)

### 3.1 전송 타입 추가

```c
/* sensor_streamer.h */
typedef enum {
    STREAM_TRANSPORT_UDP    = 0,   /* 기존 */
    STREAM_TRANSPORT_TCP    = 1,   /* 기존(미구현) */
    STREAM_TRANSPORT_SERIAL = 2,   /* 신규 — USB 직결 */
} stream_transport_type_t;
```

### 3.2 전송 분기 — 패킷 조립부는 불변

`tx_task`의 패킷 조립 로직(헤더 채우기, 샘플 복사)은 **전혀 수정하지 않는다.**
완성된 패킷을 내보내는 부분만 분기시킨다.

```c
/* 조립된 packet/len 전송 — 전송 수단만 다름 */
static int tx_send(const uint8_t *packet, size_t len)
{
    if (s.cfg.transport == STREAM_TRANSPORT_SERIAL) {
        return usb_serial_jtag_write_bytes(packet, len, pdMS_TO_TICKS(100));
    }
    /* 기존 UDP 경로 — ENOMEM 재시도 루프 포함, 그대로 유지 */
    return sendto(s.sock, packet, len, 0,
                  (struct sockaddr *)&s.dest, sizeof(s.dest));
}
```

**이 구조의 핵심 이점**: 패킷 포맷이 WiFi와 완전히 동일하다.
수신 측은 입력 소스만 바꾸면 되고 파싱 로직을 그대로 쓴다.

### 3.3 start/stop 변경

`sensor_streamer_start()` 에서 시리얼 모드일 때:

1. **소켓 생성·`server_ip` 검증을 건너뛴다**
   현재 코드는 `!cfg->server_ip` 이면 `ESP_ERR_INVALID_ARG` 로 거부한다.
   이 조건을 시리얼일 때 면제해야 한다.
2. `usb_serial_jtag_driver_install()` 로 드라이버 설치 (TX 버퍼 크기는 3.5 참조)
3. `esp_log_level_set("*", ESP_LOG_NONE)` 으로 로그 차단
4. 이전 로그 레벨을 보관해 stop 시 복원

`sensor_streamer_stop()` 에서:
- `usb_serial_jtag_wait_tx_done()` 으로 잔여 데이터 전송 완료 대기
- 로그 레벨 복원
- `usb_serial_jtag_driver_uninstall()`
- 기존 소켓/링버퍼 정리 경로는 그대로

### 3.5 TX 버퍼 크기 — 기본값 사용 금지

**ESP-IDF 기본값은 256바이트다** (`USB_SERIAL_JTAG_DRIVER_CONFIG_DEFAULT`).
패킷 하나가 1,216바이트이므로 기본값을 쓰면 **매 전송마다 블로킹**이 발생한다.
tx_task가 막히면 링버퍼가 차고 센서 샘플이 유실된다.

```c
usb_serial_jtag_driver_config_t ucfg = USB_SERIAL_JTAG_DRIVER_CONFIG_DEFAULT();
ucfg.tx_buffer_size = 8192;   /* 패킷 1216B × 약 6.7개 분량 */
```

**8192B 선정 근거**: 26.6 kHz에서 초당 약 133패킷(162 KB/s)이 발생한다.
8 KB는 약 50 ms 분량의 여유로, USB 호스트 측 일시 지연을 흡수한다.
이 값은 실측(8.2 고속 유실 검증)에서 `dropped` 가 발생하면 상향 조정한다.

> `usb_serial_jtag_write_bytes()` 는 tx_buffer_size > 0 일 때
> TX 링버퍼에 복사 후 즉시 반환하므로, 버퍼가 충분하면 tx_task가 막히지 않는다.

### 3.4 로그 차단의 안전장치

로그를 껐더라도 차단 시점 이전에 버퍼에 쌓인 잔여 로그가
첫 패킷 앞에 섞여 나갈 수 있다.

**대응**: 수신 측이 magic(`0x49495333`)을 스캔해 패킷 경계를 찾는다.
앞부분 쓰레기 바이트는 자동으로 버려진다.
기존 `udp_receiver.py` 에 이미 magic 검사가 있으므로 같은 방식이다.

## 4. NVS 설정 구조 (config_manager)

### 4.1 구조체 변경 없음

```c
typedef struct {
    char     server_ip[CONFIG_MGR_IP_MAX_LEN + 1];
    uint16_t server_port;
    uint8_t  rate_step;
    uint8_t  transport;   /* 0=UDP, 1=TCP, 2=USB시리얼 ← 값 2 추가 */
    uint8_t  read_mode;
} config_stream_t;
```

필드 추가 없이 `transport` 가 받는 **값의 범위만 확장**한다.

**기존 디바이스 호환성**: NVS 네임스페이스(`devcfg`)와 키가 그대로이므로,
이미 설정된 디바이스는 `transport=0` 으로 읽혀 기존 UDP 동작을 유지한다.
마이그레이션 불필요.

### 4.2 시리얼 모드에서 server_ip 처리

시리얼 모드에서 `server_ip`/`server_port` 는 사용되지 않지만
**필드는 유지하고 기존 값도 보존한다.**
나중에 WiFi 모드로 되돌릴 때 사용자가 서버 IP를 다시 입력하지 않아도 된다.

## 5. 부팅 분기 (main.c)

### 5.1 전송 방식에 따른 초기화 분기

현재 흐름은 `WiFi 연결 → 성공 시 스트리밍 시작` 이다.
앞단에 전송 방식 분기를 넣는다.

```
설정 로드 (config_manager_load_stream)
  │
  ├─ transport == 2 (USB 시리얼)
  │    ├→ WiFi 초기화를 건너뜀
  │    │   (현재 최대 60초 연결 대기가 사라져 부팅이 빨라지고 소비전력 감소)
  │    ├→ 센서 초기화
  │    ├→ 3초 명령 대기 창 (5.2 참조)
  │    ├→ 로그 차단
  │    └→ 시리얼 스트리밍 시작
  │
  └─ transport == 0/1 (WiFi)
       └→ 기존 흐름 그대로 (WiFi 연결 → 스트리밍)
```

### 5.2 3초 명령 대기 창 — 복구 경로

**문제**: 시리얼 모드에서 스트리밍이 시작되면 USB 포트가 데이터로 가득 차고
로그도 꺼진다. 이 상태에서는 `serial_protocol` 의 JSON 명령 응답(`#RESP#`)이
데이터와 충돌해 Config Tool이 디바이스에 접근할 수 없다.

**대응**: 스트리밍 시작을 **부팅 후 3초 지연**시킨다.
이 3초 동안 `serial_protocol` 이 정상 동작하며 설정 변경·공장 초기화 명령을 받는다.

이 창이 **시리얼 모드 디바이스의 유일한 복구 경로**이므로 반드시 구현해야 한다.
이것이 없으면 한 번 시리얼로 설정한 디바이스는 GUI로 되돌릴 수 없다.

> 참고: 공장 초기화는 NVS 직접 주입 방식(6.3)을 쓰므로 이 창과 무관하게 동작한다.
> 3초 창은 향후 JSON 명령 기반 기능을 위한 안전장치 성격이 크다.

## 6. GUI 변경 (config-tool)

### 6.1 전송 방식 선택 UI (2단계 화면)

2단계 최상단에 전송 방식 선택을 추가하고, 선택에 따라 하위 입력란을 전환한다.

```
┌─ 데이터 전송 방식 ──────────────────────┐
│  ◉ WiFi 무선 전송                        │
│     센서가 WiFi에 접속해 서버로 전송       │
│  ○ USB 직결 전송                         │
│     케이블로 PC에 직접 전송 (WiFi 불필요)  │
└────────────────────────────────────────┘
```

| 선택 | 표시할 입력란 |
|------|-------------|
| WiFi | WiFi SSID/비번 + 서버 IP/포트 + 속도 + 읽기방식 (현재와 동일) |
| USB 직결 | 속도 + 읽기방식만 |

USB 선택 시 안내 문구:

> 💡 USB 케이블로 연결된 PC가 데이터를 받습니다. 최대 26.6 kHz까지 사용 가능합니다.
> ⚠️ 전송 중에는 디바이스 로그가 표시되지 않습니다.

**보드레이트는 GUI에 노출하지 않는다.** USB CDC에서 무의미한 값이며,
노출하면 사용자가 속도 제약으로 오해할 수 있다.

### 6.2 저장 후 검증 (3단계)

전송 방식에 따라 검증 방법이 다르다.

| 모드 | 검증 내용 |
|------|----------|
| WiFi | 현행 유지 — WiFi 연결 성공 + 서버로 데이터 도착 |
| USB 직결 | **시리얼 포트로 패킷이 실제 수신되는지 확인** |

USB 검증은 부팅 후 3초 창이 지난 뒤 시작되는 패킷 스트림에서
magic(`0x49495333`)을 스캔해 유효 패킷 수를 센다.
데이터가 실제로 흐르는 것을 직접 확인하므로 WiFi 방식보다 검증이 직접적이다.

### 6.3 공장 초기화 버튼

**위치**: 1단계 화면 하단, 기존 "고급: 펌웨어 재설치" 링크 옆.
실수 클릭을 막기 위해 동일한 `adv-link` 작은 링크 스타일 사용.

**구현 방식**: 펌웨어의 `factory_reset` JSON 명령이 아니라
**빈 NVS 바이너리 주입** 방식을 쓴다.

| 방식 | 장단점 |
|------|-------|
| **빈 NVS 주입 (채택)** | 이미 검증된 경로 재사용. 디바이스 상태와 무관하게 확실히 동작 |
| JSON 명령 | 3초 창을 놓치면 실패. 시리얼 모드에서 불안정 |

**동작 절차**:
1. 버튼 클릭
2. 확인 대화상자 — "설정이 모두 지워집니다. 펌웨어는 유지됩니다."
3. 빈 NVS 바이너리를 `0x9000` 에 주입
4. 완료 안내 — "초기화 완료. 다시 설정할 수 있습니다."

### 6.4 Tauri 백엔드 변경 (lib.rs / nvs.rs)

| 함수 | 변경 |
|------|------|
| `write_config` | `transport` 파라미터 추가 → `generate_full_nvs` 가 값 2 기록 |
| `verify_serial_stream(port)` | **신규** — 시리얼에서 패킷 수신 확인 |
| `factory_reset(port)` | **신규** — 빈 NVS 주입 |

## 7. WDAQ 수신 측 계약 (송신 사양)

**이 장은 라즈베리파이(EDU Kit WDAQ) 수신 프로그램 개발의 입력 사양이다.**
아래 값은 모두 현재 펌웨어 코드에서 확인한 실제 값이다.

### 7.1 패킷 구조

```c
/* 16바이트 헤더 — packed, 리틀엔디안 */
typedef struct __attribute__((packed)) {
    uint32_t magic;        /* 0x49495333 ("IIS3") */
    uint8_t  version;      /* 1 */
    uint8_t  rate_step;    /* 0~4 */
    uint16_t sample_count; /* 이 패킷의 샘플 수 */
    uint32_t seq;          /* 패킷 시퀀스 번호 */
    uint32_t timestamp_ms; /* 부팅 후 경과 ms */
} stream_header_t;
```

헤더 뒤에 `sample_count × 3 × int16` (리틀엔디안) 샘플 배열이 따른다.
샘플 1개 = X, Y, Z 각 int16 = 6바이트.

**Python 파싱 (기존 udp_receiver.py와 동일):**

```python
MAGIC = 0x49495333
HEADER = struct.Struct("<IBBHII")   # 16 bytes
magic, ver, rate_step, count, seq, ts = HEADER.unpack_from(data, 0)
samples = struct.unpack_from("<%dh" % (count * 3), data, HEADER.size)
```

### 7.2 패킷 크기

| 항목 | 값 |
|------|-----|
| 패킷당 샘플 수 | 200 (`STREAM_SAMPLES_PER_PACKET`) |
| 헤더 | 16 B |
| 페이로드 | 200 × 6 = 1,200 B |
| **총 패킷 크기** | **1,216 B** |

### 7.3 rate_step → 샘플레이트 매핑

```python
RATE_HZ = {0: 1000, 1: 3333, 2: 6667, 3: 13333, 4: 26667}
```

### 7.4 시리얼 포트 설정

| 항목 | 값 |
|------|-----|
| 보드레이트 | 115200 (USB CDC이므로 실제 속도와 무관, 아무 값이나 동작) |
| 데이터 형식 | 8N1 |
| 포트 (라즈베리파이) | `/dev/ttyACM0` |

### 7.5 스트림 동작 특성

**반드시 고려해야 할 사항:**

1. **시작 시점**: 부팅 후 약 3초 (명령 대기 창 이후)
2. **경계 동기 필수**: 스트림 선두에 부팅 로그 잔여 바이트가 섞일 수 있으므로,
   magic 스캔으로 패킷 경계를 찾아야 한다
3. **단방향 송신**: 디바이스는 시작하면 **무조건 계속 송신**한다.
   수신 측 상태와 무관하다

### 7.6 GPIO 게이팅 시 주의사항

포토센서 False 로 수신을 중단해도 **디바이스는 송신을 멈추지 않는다.**
이번 범위의 디바이스는 단방향 구조다. 따라서 WDAQ 측에서:

| 방식 | 주의점 |
|------|-------|
| 데이터를 읽되 버리기 | 단순하고 안전. 재개 시 동기 유지됨 |
| 포트를 닫았다 다시 열기 | 재개 시 **magic 재동기 필수** (패킷 중간부터 읽힘) |

**중단 구간이 길 경우**: OS 시리얼 입력 버퍼에 오래된 데이터가 쌓인다.
재개 직후 과거 데이터가 먼저 나오므로 `ser.reset_input_buffer()` 로
버퍼를 비우고 시작하는 것이 깔끔하다.

> 디바이스가 실제로 송신을 멈추게 하려면 별도 제어 채널이 필요하며,
> 현재 설계 범위에 없다. 필요 시 별도 작업으로 다룬다.

### 8.1 환경 제약

- **펌웨어(1~3)**: 이 macOS 환경에 ESP-IDF가 설치되어 있지 않아 빌드 불가.
  코드 작성은 가능하나 **빌드·실기기 검증은 라즈베리파이에서** 해야 한다.
- **GUI(4~5)**: macOS에서 `cargo`/`npm` 으로 빌드·테스트 가능.

### 8.2 필수 검증 항목

| 항목 | 기준 |
|------|------|
| **고속 유실 검증** | 26.6 kHz에서 `dropped` 통계 — 실제 상한 확정. 유실 시 TX 버퍼(3.5) 상향 후 재측정 |

## 9. 미해결 사항

1. **26.6 kHz 실제 달성 여부** — 2장 참조. USB Serial/JTAG FIFO 제약으로
   고속에서 유실이 발생할 수 있다. 실측 후 GUI 속도 옵션 상한을 조정할 수 있다.
2. **TCP 전송** — 기존부터 미구현 상태(`STREAM_TRANSPORT_TCP`). 이번 범위 밖.
